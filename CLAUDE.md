# Yoshlar Radar — контекст проекта

Хакатон-прототип внутреннего дашборда для хокимията Мирзо-Улугбекского района
(Ташкент): мониторинг занятости молодёжи по 12 махаллям. Весь UI на русском,
все данные синтетические и генерируются на клиенте.

## Читай первым: если задача звучит как «покрась карту в разные цвета»

Категориальная раскраска **уже написана и работает**, и с 14.08.2026 она стоит
по умолчанию: карта при открытии показывает 12 разных цветов, соседние зоны
заведомо различимы. Не строй раскраску заново.

Если пользователь всё равно видит красно-оранжевую карту — он либо переключил
`ToggleGroup` на «По статусу NEET», либо смотрит на мёртвый порт. Проверь порт
первым делом: такая путаница уже была.

## Стек и запуск

React 19 + TypeScript + Vite 8 + TanStack Start/Router + Tailwind v4 + shadcn/ui
+ react-leaflet 5. Приложение живёт в подкаталоге `front/`, репозиторий — в корне.

```bash
cd front
npm install
npm run dev      # http://localhost:8080 — порт задан в vite.config.ts
npm run build
npx tsc --noEmit
```

**Всегда проверяй на `localhost:8080`.** Если Vite скажет «Port 8080 is in use»
и уедет на 8081 — значит сервер уже поднят, не поднимай второй: у пользователя
уже была путаница, когда он смотрел на мёртвый 8081 и решил, что правки не
применились.

**Никогда не делай `pkill -f "vite dev"`** — под маску попадает dev-сервер
пользователя. Свои фоновые процессы убивай по конкретному PID.

## Git

**Работаем прямо в `main`: без веток, без PR.** Коммит → push в `main`.
Remote: `git@github.com:tiredjon/nexus.git`.

Правило сменилось 20.08.2026 — раньше здесь требовались ветка → PR → зелёные
чеки. Причина отказа: репозиторий оброс девятью ветками, восемь из которых были
уже влиты squash'ем, и понять по `git log`, что влито, стало невозможно (squash
переписывает хеши, поэтому влитые ветки показываются как невлитые — сверять надо
`git cherry` по patch-id). Плюс PR-гейт ничего не давал фронту: CI
(`.github/workflows/backend-ci.yml`) покрывает только `back/`.

Раз CI фронт не страхует — проверяй правки фронта сам перед push: `npx tsc
--noEmit` (2 известные ошибки ниже — норма) и живая проверка в headless Chrome
по рецепту из раздела «Как проверять карту в браузере». По бэку остаются тесты:
`npm test` в `back/`.

## ИИ-фичи (`front/src/lib/ai.ts`)

Пять ИИ-фич фронта: разбор заметки с обхода, объяснение рекомендации, сводка
дашборда, официальная справка на аналитике, подбор вакансий/курсов на карточке
человека. Все идут через **один** серверный вызов `aiGenerate` в
`src/lib/ai-server.ts` (TanStack `createServerFn`, исполняется только на сервере
— API-ключ в браузер не утекает). При любой ошибке фичи тихо падают на
детерминированные `*Fallback` в `ai.ts`, поэтому всегда что-то показывают.

**Провайдер — Google Gemini** (с 20.08.2026; до этого был DeepSeek — прошлая
реализация в git-истории `ai-server.ts`). Переключено потому, что у нас на руках
рабочий ключ Gemini, а ключа DeepSeek нет.

**Оговорка про хостинг остаётся в силе:** Google блокирует Gemini по стране
egress-IP (`User location is not supported`), поэтому с российского сервера
фичи молча уйдут в фолбэк. Локально и на Vercel работает. Если прод переедет
в РФ — нужен прокси или возврат к DeepSeek.

- Модель по умолчанию `gemini-3.7-flash` (`GEMINI_MODEL` в `front/.env`, ключ
  `GEMINI_API_KEY`). Запасная стабильная — `gemini-2.5-flash` (одна строка
  в `.env`), обе проверены в JSON-режиме.
- Ключ уходит заголовком **`x-goog-api-key`**. В `Authorization: Bearer` тот же
  ключ отдаёт 401 `API_KEY_SERVICE_BLOCKED` — там API ждёт OAuth-токен.
- Версия API — **`v1alpha`**, не `v1beta`: модели 3.x на `v1beta` отвечают 404.
- Flash 3.x «думает»: в ответе часть элементов `content.parts` помечена
  `thought: true` — это размышления, не ответ. Берём только части без этого
  флага, иначе мышление попадёт в `JSON.parse`. JSON гарантируется
  `responseMimeType: application/json` + структурой прямо в промпте
  (`responseSchema` не используем, объекты `SCHEMA_*` в `ai.ts` декоративные).
- Смена провайдера изолирована в `ai-server.ts` — трогается один файл, `ai.ts`
  и компоненты нет.
- Успешные ответы кэшируются в памяти модуля на сессию. Тяжёлые (справка,
  дашборд-сводка) прогреваются при входе (`src/lib/prewarm.ts`) — на демо
  мгновенны. Карточки людей прогреть заранее нельзя: открой нужного человека
  вручную перед показом, ответ закэшируется.
- `.env` (с ключом) в git не коммитим — он в `.gitignore`; шаблон —
  `front/.env.example`.

### Деплой фронта на Vercel

Проект — `yoshlar-radar` (создан 21.08.2026, `front/.vercel/project.json`).
Деплоим **туда, а не в РФ**, иначе Gemini отвалится по гео-блоку.

- `GEMINI_API_KEY` и `GEMINI_MODEL` заведены в Vercel на все три окружения
  (production/preview/development). `.env` не деплоится, на проде работает
  только `process.env` — fs-фолбэк из `getKey()` в serverless-бандле мёртв.
- **`maxDuration` задаётся в `vite.config.ts`** через
  `nitro({ vercel: { functions: { maxDuration: 60 } } })`, а не в `vercel.json`:
  nitro собирает Build Output API, и поле `functions` из `vercel.json` туда не
  доезжает. Проверять так: `.vercel/output/functions/__server.func/.vc-config.json`.
  Дефолтные 10 с мало — справка отвечает 6–7 с и с ретраем упирается в лимит.
- Общий бюджет ретраев в `ai-server.ts` (`TOTAL_BUDGET_MS` 45 с) держим **ниже**
  `maxDuration`: если функцию убьют по лимиту, фолбэк не успеет выполниться и
  пользователь увидит вечный спиннер вместо заглушки.
- `vercel link` дописывает в `front/.gitignore` строки `.vercel` и `.env*`.
  Вторая идёт после `!.env.example` и утаскивает шаблон под игнор — порядок
  правил поправлен, при повторном `link` проверь снова.

## Бэкенд (`back/`)

Спека и пошаговые сессии — в `backend.md` (единственный источник правды по API).
Бэкенд в отдельном каталоге `back/`, фронт в этих сессиях не трогаем. Стек:
Node 22 + TypeScript (ESM) + Fastify 5 + Drizzle ORM + PostgreSQL 16, тесты —
vitest через `app.inject()` против реального Postgres. Порты: API `3001`,
dev-Postgres `5438` (не пересекается с фронтом на `8080`).

Готово (S1): каркас, схема БД (3 таблицы `mahallas`/`people`/`history_events`
на text+CHECK, миграция `back/drizzle/0000_*.sql` с `pg_trgm` и partial/GIN
индексами), `GET /health`, CI `.github/workflows/backend-ci.yml`.

Готово (S2 + sync-front-model): auth на `@fastify/jwt` (HS256, TTL 12ч;
`src/plugins/auth.ts` + `authenticate` preHandler), `POST/GET /api/auth/login|me`,
`GET /api/meta/mahallas|dictionaries`, константы-порт из фронта
(`src/db/constants.ts`), детерминированный сидер (`generatePeople` порт,
`mulberry32(20260814)`; флаги `--count/--anchor/--append/--lightHistory`).

**Важно:** после S1/S2 бэк был синхронизирован с объединённым фронтом
(sync-front-model): модель `Person` в схеме/сидере — **полная** модель актуального
`front/src/lib/data.ts` (~40 полей, `skills/languages` как `text[]`, блок
программы `programOutcome/programRoutedAt/routedBy`, миграция `0001_*.sql`).
Роли — **5 штук** из `front/src/lib/permissions.ts` (`mahalla_officer`,
`youth_rep`, `district_officer`, `employment_specialist`, `admin`);
`resolveScope` (`src/lib/scope.ts`) маппит роль в scope
`own_mahalla/all_mahallas/routed_only/all_data`. Старые роли `district/mahalla`
логином не принимаются.

Готово (S3): реестр — `GET /api/people` (п.6) с фильтрами, поиском, пагинацией и
сортировкой русской коллацией; `GET /api/people/:id` (п.7) с полным профилем и
историей. Вся фильтрация в SQL: динамический WHERE через drizzle `and()`, `total`
отдельным `count(*)`, whitelist-мапа сортировок (значение из query никогда не
попадает в `ORDER BY`), вторичный ключ по `id` — иначе страницы «плывут» при
равных значениях. Скоуп берётся из `resolveScope().kind`: `own_mahalla` → только
своя махалля (чужой `?mahalla=` → 403), `routed_only` → только `program IS NOT
NULL`, `all_mahallas`/`all_data` → без ограничений. Сериализаторы `toPerson()`/
`toPersonListItem()` (`src/lib/serialize.ts`) отдают полную модель Person с
`mahalla` именем-строкой.

Готово (S4): мутации карточки — `POST /api/people/:id/route-to-program` (п.8),
`confirm-status` (п.9), `request-clarification` (п.10), `PATCH .../review-status`
(п.11). Все четыре в `src/routes/mutations.ts` через общий `mutatePerson()`: одна
транзакция, `SELECT … FOR UPDATE` по `people`, проверка скоупа тем же
`assertVisible()`, что и чтение, апдейт + вставка history, ответ — полный `Person`.
«Сегодня» = `CURRENT_DATE` на стороне БД. Важные тонкости: у
`request-clarification` `last_update` **не меняется**; `confirm-status` трогает
`neet_review_status` только когда `neet = true`; `route-to-program` дополнительно
пишет `programOutcome/programRoutedAt/routedBy` и `source='программа'` в историю —
как это делает фронт. Хелперы `fetchPersonRow/fetchHistory/assertVisible` вынесены
в `routes/people.ts` и переиспользуются мутациями (тип `Runner` в `db/client.ts`
позволяет звать их и внутри транзакции).

Готово (S5): агрегаты — `GET /api/stats/dashboard` (п.12), `map` (п.13),
`review` (п.14), `analytics` (п.15) в `src/routes/stats.ts`. Все числа считает
Postgres: `count(*) FILTER (WHERE …)` за один проход, разрезы — `GROUP BY
mahallas.id`; в JS остались только две демо-формулы (`neetTrend`, `monthly`),
которым нужны уже готовые скаляры. Разрезы по махаллям идут **от таблицы
`mahallas` через LEFT JOIN** (скоуп людей — в `ON`), чтобы пустые махалли
остались в ответе нулями, как их рисует фронт; `share` = `round(neet*100 /
NULLIF(total,0), 1)` с `COALESCE(…,0)` — деления на ноль нет. Скоуп общий с
S3/S4: `scopeConditions()` экспортирована из `routes/people.ts` и переиспользуется
всеми агрегатами; для own_mahalla дополнительно сужается и список махаллей.
Канбан — 4 отдельных запроса с `LIMIT 40` на колонку (обрезка тоже в SQL).

Готово (S6): демо больших данных + полировка. `scripts/bench.ts` (`npm run
bench -- [--n 30] [--base URL]`) логинится `admin`'ом против уже запущенного
сервера и печатает markdown-таблицу min/p50/p95/max для `/api/people`
(фильтр+поиск+пагинация), `/api/stats/dashboard`, `/api/stats/map`. Сидер
проверен на `--count 100000 --lightHistory` (~18 c). `EXPLAIN (ANALYZE,
BUFFERS)` на 100k строк подтвердил, что trigram-поиск по ФИО и group-by
дашборда уже используют нужные индексы — чинить было нечего; полные
транскрипты, тайминги и talk-track для жюри — в `backend.md`, раздел 9.

## Карта района (`/map`) — главное

### Слои по зуму

`DistrictMap.tsx` → `MapLayers` переключает слой по текущему зуму:

| Зум | Слой |
|-----|------|
| < 9 | `RegionsLayer` — 14 областей Узбекистана |
| 9–12 | `DistrictsLayer` — 10 районов Ташкента |
| ≥ 13 | `MahallaZones` — 12 территорий махаллей |

**Зоны махаллей видны только на зуме 13+.** При открытии страницы `MapBridge`
через 500 мс запускает `flyTo(DISTRICT_CENTER, DISTRICT_ZOOM)` и карта сама
долетает до нужного масштаба. Если видишь контуры областей/районов — это не
поломка, а просто мелкий масштаб; кнопка «Вернуться к району» справа сверху.

### Как построены территории

Официальных границ махаллей в открытых geo-датасетах нет. Территории строятся
в `src/lib/mahallaVoronoi.ts` как диаграмма Вороного от координат-центров
махаллей, обрезанная по контуру района (`d3-delaunay` + `@turf/turf`).
Проверено: сумма площадей 12 зон точно равна площади района (coverage 1.0000),
без нахлёстов и выходов за границу.

**Важная особенность данных.** Координаты в `MAHALLA_COORDS` (`src/lib/data.ts`)
синтетические и заданы по реальному городу, а контур района берётся из
geoBoundaries (ADM2) и смещён примерно на 0.03° к юго-западу. Из-за этого
только 3 точки из 12 попадают внутрь полигона. Прямая обрезка Вороного дала бы
9 пустых зон. Поэтому `fitSeedsToDistrict()` аффинно вписывает облако точек в
bbox района и притягивает внутрь те, что попали в вогнутости. Взаимное
расположение махаллей сохраняется. Сами данные не трогались — вся компенсация
изолирована в одной функции, её легко выкинуть, если появятся настоящие
координаты.

Ещё в файле есть 2 шага релаксации Ллойда: без них разброс площадей был
1.07–5.17 км², с ними 1.2–4.3 км².

`DISTRICT_CENTER` в `src/lib/map-geo.ts` — центр bbox полигона района
(`[41.3015, 69.3145]`), подобран так, чтобы все зоны помещались в кадр.
Старое значение лежало выше северной границы, и половина зон уходила за экран.

Зона «Дархан» разрезана на два куска — это реальная вогнутость границы района,
а не баг отрисовки. `positions` отдаётся в формате Leaflet `LatLng[][][]`
(мультиполигон), иначе второй кусок отрисовался бы дыркой.

### Раскраска — тут два режима, оба уже сделаны

`src/lib/mahalla-colors.ts` + переключатель `ToggleGroup` на `/map` над картой
справа. Режим хранится в `useState` на странице, дефолт — `"mahalla"`.

- **«По махаллям»** (дефолт) — категориальная палитра `MAHALLA_COLORS`,
  12 насыщенных цветов, `fillOpacity` 0.45, на hover 0.65, контур — тот же цвет
  через `darken()`. Легенда — сетка из 12 махаллей.
- **«По статусу NEET»** — emerald / amber / red по доле NEET, `fillOpacity`
  0.35, на hover 0.55. Легенда — три статусных порога.

Цвет закреплён за махаллёй (а не за позицией в переданном списке) — чтобы
инспектор махалли видел тот же цвет, что и в общем виде района.

Вся развилка собрана в одной функции `zoneStyle(stat, mode)` в
`DistrictMap.tsx` — новые режимы добавлять туда.

### Как цвета разводятся между соседями

Раньше цвет брался по индексу махаллы в списке, а порядок списка с географией
не связан — соседние зоны получали близкие оттенки (teal/emerald, pink/red).
Сейчас палитра раздаётся по графу смежности:

- `mahallaNeighbors()` в `mahallaVoronoi.ts` отдаёт соседей каждой зоны — это
  рёбра триангуляции Делоне по тем же центрам, что и у Вороного (считается по
  тем же релаксированным центрам, что и геометрия, через `relaxedSeeds()`).
- `assignPalette()` в `mahalla-colors.ts` жадно раздаёт цвета: сначала зоны
  с наибольшим числом соседей, каждой — самый далёкий (по «redmean») из ещё
  свободных цветов. Каждый цвет уходит ровно одной махалле, поэтому в легенде
  оттенки не повторяются; обычная раскраска графа обошлась бы 4–5 цветами и
  для легенды не годится.
- Раскладка считается один раз лениво и кэшируется в модуле.

Раскладка зависит только от констант (`MAHALLA_COORDS` + контур района), так
что она детерминирована, но при правке координат цвета могут перетасоваться.

### Что менять НЕ надо

Логика Вороного и обрезки turf, попапы по клику (мини-карточка со статами +
кнопка «Открыть махаллю» → `/registry?mahalla=…`), подписи-тултипы в центре
зон. Подписи висят на отдельном некликабельном `Marker` с пустой `divIcon`
(`interactive={false} keyboard={false}`), потому что штатный тултип полигона
Leaflet ставит в геометрический центр, который у вогнутых зон попадает наружу.

## Состояние линта и типов (было таким ДО правок по карте)

- `npx tsc --noEmit` даёт 2 ошибки: `DistrictMap.tsx` (`getElement()?.style`)
  и `vite.config.ts` (`noImplicitReturns`). Обе в коде, который правки по карте
  не трогали.
- `npm run lint` даёт ~785 ошибок форматирования по всему репозиторию: в
  проекте нет `.prettierrc`, поэтому prettier требует `printWidth: 80`, а весь
  код написан под ~100. Одна строка конфига сделает линт зелёным — с
  пользователем не согласовано.

Новый код форматируй под окружающий стиль (~100 символов), а не под дефолт
prettier.

## Как проверять карту в браузере

Расширение Claude in Chrome в этой среде не подключено. Проверка делается через
headless Chrome по CDP — рабочий рецепт:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
```
